Formulas, freshness & setup notes

Total traffic = attributed installs + blocked installs. Clean installs = attributed installs − post-attribution installs. Blocked %, PA % and Total fraud % all use total traffic as denominator.
Raw installs_report is used first so PRT/Site ID/Campaign breakdown stays available. If raw access fails, returns 0 rows, or no configured PID/PRT row matches, aggregate partners_by_date_report is automatically used. PID-matched aggregate rows remain separate; when the aggregate report has valid installs but no usable PID dimension, P360 retains one app-level aggregate total and collapses blocked/PA into the same scope. Aggregate fallback does not provide reliable Site ID/Campaign/publisher-rate detail. Raw requests use a 1,000,000-row cap and the dashboard marks the run incomplete if the cap is reached.
Publisher IDs are read dynamically from af_ad first and af_adset as fallback. Any suffix after the first underscore is removed, so 282_132048808 is grouped as publisher 282. No publisher IDs are hardcoded. Publisher fraud rates require the publisher field to be populated consistently across attributed, blocked and post-attribution rows; the publisher section shows field coverage and warns when aggregate install fallback prevents publisher-level install attribution.
Billable Events count exact, case-sensitive matches from AppsFlyer's real-time raw in_app_events_report. Only the event name saved on that App + PID + PRT row is counted. The Protect360 blocked_in_app_events_report and blocked-event postbacks are never requested or included.
Impressions are read from AppsFlyer's aggregate partners_by_date_report and included only when its media source matches a configured PID/PRT scope. The aggregate response is cached and reused by install fallback and click comparison when applicable. Publisher-level impressions are unavailable because this aggregate report does not contain af_ad/af_adset.
The click comparison is app-level. Affise raw clicks from all configured Offer IDs are compared with AppsFlyer partners_by_date_report clicks matching the selected app's configured PIDs. Affise hosts/unique clicks are not used. Affise click statistics are mapped by offer because Affise supports click filters by date, offer and affiliate—not advertiser. Daily boundaries can differ if the Affise account timezone does not match the AppsFlyer app timezone.
Post-attribution data is updated later than real-time blocked data. Today/recent ranges are provisional and can change. Each enabled Apps Excel row is treated as a separate App + PID + optional PRT scope. Different PIDs are never merged in the default PID × App view. The orange Global Report Filters bar can filter every view by PID, PRT, Account, App, App ID, Campaign and Day. KPIs, publisher reporting and filtered CSV exports follow the same scope. API calls for the same app are fetched once internally only to save quota; calculations remain separate. Each app uses its configured Reporting Timezone. The timezone value must match that app's AppsFlyer App Settings. AppsFlyer tokens are selected server-side from the PRT ID and are never sent to the browser. The most recently uploaded Excel configuration is saved on the persistent disk and automatically loaded for all team members until it is replaced or removed.
